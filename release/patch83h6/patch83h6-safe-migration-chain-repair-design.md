# Patch 83H.6: Safe Migration-Chain Repair Design

## Statement of Intent
This document provides an analysis and recommended safe repair strategy for the local migration chain regression caused by the 016->055 reorder. **No repair was applied in this patch.**

## 1. Verified Historical Timeline
- **`f2271a3`**: The original migration `016_rollout_onboarding_user_guides.sql` was authored. It created `public.restore_dry_run_jobs` and included legacy columns such as `title`, `findings`, and `tested_by`. Shortly after, `022_ultra_release_restore_admin_dictionary.sql` was added, assuming 016 had run and therefore explicitly updating `restore_dry_run_jobs` based on those columns.
- **`614d833`**: During a cloud schema reconciliation effort, `016_rollout_onboarding_user_guides.sql` was exactly renamed to `055_rollout_onboarding_user_guides_compat.sql`.
- **Dependency breakage**: migration 022 explicitly depends on the table schema generated by the original 016. Because 016 was renamed to 055, a fresh local reset executes 022 before the legacy columns exist.

## 2. Exact Original 016 File Content Summary
The original 016 file created tables for `grc_training_checklist`, `rollout_waves`, `rollout_wave_departments`, and `restore_dry_run_jobs`. The `restore_dry_run_jobs` definition exactly included:
```sql
create table if not exists restore_dry_run_jobs (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references organizations(id) on delete cascade,
  title text not null,
  backup_package_id uuid references backup_packages(id) on delete set null,
  status text not null default 'planned' check (status in ('planned','running','passed','failed','cancelled')),
  tested_by uuid references profiles(id) on delete set null,
  started_at timestamptz,
  completed_at timestamptz,
  findings text,
  created_by uuid references profiles(id) on delete set null,
  created_at timestamptz not null default now()
);
```

## 3. Comparison Between Original 016 and current 055
- **Identical sections**: Both files are 100% byte-for-byte identical.
- **Later modifications**: None. The file was strictly renamed by Git (`R100`).
- **Object list**: Both define `grc_training_checklist`, `rollout_waves`, `rollout_wave_departments`, `restore_dry_run_jobs`, a trigger `set_grc_training_updated_at`, a view `v_setup_readiness_checklist`, and basic read-only RLS policies.
- **Idempotency analysis**: All object creations use `CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, `DROP TRIGGER IF EXISTS`, `CREATE INDEX IF NOT EXISTS`, `ON CONFLICT DO NOTHING`, `CREATE OR REPLACE VIEW`, and `DROP POLICY IF EXISTS`. The entire file is completely idempotent.

## 4. Cloud History Scenarios

### Scenario 1: Cloud has 016 applied and 055 applied
- **Effect of restoring 016**: Safe. Supabase CLI will see 016 as already applied.
- **Effect of modifying 022**: Risky. Modifying 022 alters its checksum, potentially breaking `supabase db push` unless repaired remotely.

### Scenario 2: Cloud has 016 applied but 055 not applied
- **Effect of restoring 016**: Safe. It’s already applied. 055 would run as a new migration, but is 100% idempotent so it will gracefully skip.
- **Effect of modifying 022**: Risky (checksum mismatch).

### Scenario 3: Cloud has 055 applied but 016 not applied
- **Effect of restoring 016**: 016 would be detected as an "out-of-order" unapplied migration. Depending on CLI version, `supabase db push` might execute it out-of-order or reject it. Because it is idempotent, execution is technically safe, but the history warning could disrupt CI/CD.

### Scenario 4: Fresh local database has neither applied
- **Effect of restoring 016**: Resolves the local reset blocker perfectly.
- **Effect of modifying 022**: Resolves the local reset blocker perfectly, but breaks any environment that already applied the original 022.

### Scenario 5: Developer database has partially applied chain
- **Effect of restoring 016**: Developer must run `supabase db reset`.

## 5. Supabase Migration-History Risks
- **Out-of-order migration detection**: If 016 is restored, environments missing 016 but possessing later migrations will see it as a new pending migration.
- **Checksum drift**: Modifying 022 directly changes the hash tracked in `supabase_migrations.schema_migrations`. Subsequent pushes will throw a mismatch error unless `supabase migration repair` is executed.

## 7. Recommended Repair Approach
**Option A: Restore the exact original `016_rollout_onboarding_user_guides.sql`.**
Because 055 is 100% identical and fully idempotent, having both 016 and 055 in the repository is technically safe. Local resets will execute 016, satisfying 022. Later, 055 will execute harmlessly as a no-op.
*Condition:* We must verify read-only cloud migration history to ensure restoring 016 does not cause fatal out-of-order CI deployment blocks.

## 8. Recommended Exact Implementation Sequence
1. Obtain remote migration history from production/staging.
2. If safe, execute `git checkout f2271a3 supabase/migrations/016_rollout_onboarding_user_guides.sql`.
3. Do not modify 022 or 055.
4. Run `supabase db reset` locally to confirm success.
5. Push to a branch and test CI/CD against staging.

## 10. Stop/Go Gates
- **STOP:** If remote CI/CD strictly rejects out-of-order migrations and 016 is unapplied remotely.
- **GO:** If remote history confirms 016 is already applied, or if `supabase db push` accepts idempotent out-of-order files.

## 11. Rollback Strategy
If restoring 016 breaks the cloud deployment, delete `016_rollout_onboarding_user_guides.sql` from the repository and commit. No remote schema repair is needed because it is idempotent.
